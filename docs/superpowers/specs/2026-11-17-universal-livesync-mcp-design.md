# Design: универсальный MCP-сервер для Self-hosted LiveSync (CouchDB + S3)

Дата: 2026-11-17. Статус: черновик на согласование.
Опорные материалы: `docs/AUDIT-2026-11-10.md` (аудит текущей CouchDB-заготовки, 69 подтверждённых находок), исходники upstream `vrtmrz/livesync-commonlib` (журнальный S3-режим).

## 1. Замысел и зачем

MCP-сервер, дающий LLM-клиентам (Claude.ai, Codex и др.) доступ к vault, синхронизируемому плагином Self-hosted LiveSync, **через оба поддерживаемых плагином транспорта удалённого хранилища**:

- **CouchDB** — классический режим: удалённая база документов;
- **S3 (object storage)** — режим, где бакет содержит не базу, а append-only журнал репликации `<timestamp>-docs.jsonl.gz`.

Почему оба: существующий пользовательский деплой на S3 не должен ломать поддержку CouchDB, и наоборот. «Универсальность» = один слой инструментов, одна аутентификация, один конфиг-файл, выбор бэкенда одной переменной.

Почему не патч текущего `couchdb.py`: аудит установил, что слой хранения написан по собственной модели, расходящейся с upstream в четырёх местах, каждое из которых портит базу (B1–B4), плюс атомарность (C1) и оптимистичная блокировка (C2). Раздел 8 аудита рекомендует переписать слой хранения по образцу upstream — эта рекомендация принимается.

Ключевой факт об S3-режиме (по исходникам `livesync-commonlib`, `src/replication/journal/`): в бакете нет серверного состояния. Устройства дописывают сжатые пакеты локальных изменений и replay'ят журналы друг друга в локальную PouchDB. Следовательно, любой сторонний участник обязан быть **пиром**: replay → локальное состояние → собственные дописывания журнала. Тонкого клиента «читать объект = читать заметку» в этом режиме не существует.

## 2. Цели, не-цели, анти-цели

**Цели**
- Полный набор инструментов чтения и записи (см. §6) поверх любого из двух бэкендов.
- Формат данных, неотличимый от upstream: ревизионные цепочки, типы документов, soft delete, размеры. Записи сервера применяются живыми Obsidian-клиентами без предупреждений о повреждении.
- Безопасность данных по построению: ни одна операция сервера не может удалить или перезаписать чужие данные. Худший исход ошибки сервера — отвергнутый клиентом пакет (видимый в логе LiveSync) или обычный конфликт-диалог Obsidian, но не тихая порча.
- Фиксы всех P0/P1-находок аудита в слое инструментов (D1–D17) и слое CouchDB-хранения.

**Не-цели (в этой версии)**
- E2EE: обнаруживать и отказывать в записи, не реализовывать (B5).
- Обфускация путей (`f:`): обнаруживать и отказывать (B6).
- Hidden File Sync / синк плагинов и кастомизации (`i:`, `ix:`, `ps:`): не читать как заметки, не писать (B7, B8).
- Порт дедуплицирующего chunk-сплиттера upstream (Rabin-Karp + xxhash64) — `[DEFER]`, см. §9.
- Live-подписка на изменения (push). Достаточно refresh перед операцией.

**Анти-цели (провал, даже если «работает»)**
- Тихая потеря данных: любой ответ «успешно» обязан соответствовать реально применённому изменению (урок B3/B4: сервер отвечал «Created», файл не появлялся нигде).
- Перегрузка заметки целиком без нужды — нет, для текстовых правок это допустимая цена (upstream тоже пишет новые чанки на каждую правку).
- Второй «самодельный» формат хранения поверх LiveSync-документов.

## 3. Ограничения

- Python 3.11+ (AGENTS.md), FastMCP из `mcp[cli]` **1.x с верхней границей** `<2` (аудит A1), предпочтительно точный пин проверенной версии + lock-файл.
- Зависимости: `httpx` (CouchDB), `boto3` (S3), `aiosqlite` или sync sqlite3 в потоке (локальное состояние S3-пира; WAL-режим), `ruamel.yaml` (frontmatter), `python-dotenv`, `pydantic` (объявить явно).
- S3-эндпоинт — self-hosted (path-style); поддержка virtual-host-style не требуется, но не запрещается конфигом.
- Vault может быть большим (единицы ГБ, фото/сканы): replay потоковый, память не растёт с размером vault; бинарные чанки хранятся на диске, а не в SQLite-блобах строкой.
- Upstream-форматы сверяются на зафиксированных коммитах: `vrtmrz/livesync-commonlib` (2026-11-10) — ссылки на файлы в тексте.

## 4. Архитектура

```
LLM-клиент ──MCP──> server.py (FastMCP: auth, 20+ инструментов)
                        │
                storage_base.py  (интерфейс StorageBackend + исключения)
                  │                         │
        storage_couchdb.py          storage_journal.py
        (CouchDB, переписан         (S3 journal-пир:
         по аудиту §8) P0)           replay → SQLite + чанк-стор;
                  │                  запись → append журнала)
                  └──────── livesync_format.py ────────┘
                     (общая семантика LiveSync: path2id, типы,
                      base64-кодек newnote, shape метадокумента,
                      soft delete, chunk id)
```

- `server.py` не знает, какой бэкенд подключён, кроме как через диагностику (`vault_stats`, сообщения об ошибках).
- Выбор бэкенда: `LIVESYNC_BACKEND=couchdb|s3`, обязательно; при старте fail-fast, если переменная не задана или неполны креды выбранного бэкенда. Автодетекта нет — детерминизм важнее удобства.
- Старый `couchdb.py` удаляется (замещается `storage_couchdb.py`), история остаётся в git.

### 4.1. `livesync_format.py` — общая семантика LiveSync

Единственный источник правды о формате для обоих бэкендов (сегодня эти правила размазаны и искажены — аудит B9):

- `path2id` / `id2path` по образцу upstream (`src/string_and_binary/path.ts`): нормализация ввода (ведущий `/`, `./`, обратные слеши), экранирование ведущего `_` в `/_`, lowercase только при `handleFilenameCaseSensitive=false`, NFC-опционально (обнаруживать и отказывать, если включена).
- `is_text_doc(type, path)` — `plain` или расширение из `isPlainText` (`.md .txt .svg .html .csv .css .js .xml .canvas`).
- Кодек `newnote`: при чтении каждый чанк base64-декодируется отдельно, байты склеиваются; при записи — наоборот (аудит B4). Текстовые инструменты на бинарных файлах запрещены.
- Shape метадокумента: `_id, path, ctime, mtime (мс), size (байты декодированного тела), type, children, eden: {}`; soft delete — та же ревизия с `deleted: true` и новым `mtime`, тело сохраняется.
- Валидатор пространства имён путей (аудит B7/B10): запрещены префиксы `i:`, `ix:`, `ps:`, `h:`, `f:`, `_`, сегменты, начинающиеся с точки (`.obsidian/`), `obsydian_livesync_version`, `syncinfo`.

### 4.2. `storage_base.py` — интерфейс

Асинхронный протокол `StorageBackend`; инструменты работают только с ним:

- `startup_check()` — доступность, существование базы/бакета, чтение служебных документов; обнаружение E2EE/обфускации/case-sensitive/NFC → отказ в записи (B5/B6/B14);
- `refresh()` — привести локальное представление в актуальное состояние (для CouchDB — сброс/обновление кэша индекса; для S3 — инкрементальный replay);
- `list_notes(folder, extension, recursive)` → метаданные (path, size, mtime, type);
- `get_meta(path)`;
- `read_note(path)` → `{meta, text | bytes, is_text}` (декодированное содержимое);
- `write_note(path, content, *, create, overwrite, mtime?)` — централизованные правила D1/D2: `create` без `overwrite` на существующем — ошибка; запись в несуществующий без `create` — ошибка; воскрешение soft-deleted только через явный `create`;
- `delete_note(path)` — только soft delete;
- `rename_note(path, new_path)` — копирование `children` (не пересборка контента), сохранение `ctime`, защита same-path/case-only (D1), отказ при существующей цели без `overwrite`;
- `iterate_texts(extension)` — потоковая итерация текстов заметок с изоляцией ошибок по каждой заметке (C4): битая заметка не роняет поиск/теги/граф, а попадает в список пропущенных;
- `backend_info()` — для диагностики и `vault_stats`.

Исключения: `NoteNotFound`, `NoteExists`, `BinaryNoteError`, `ConcurrentModification`, `UnsupportedVault` (E2EE/обфускация), `StorageUnavailable`. Сообщения без внутренних URL и ревизий (аудит C7).

### 4.3. `storage_couchdb.py` — перепись CouchDB-бэкенда

Требования из аудита, все обязательны:

- **Чанки никогда не удаляются** (B1). Сборка мусора — дело встроенного GC LiveSync.
- **Soft delete** вместо HTTP DELETE (B2).
- **Типы**: любой текст — `plain`; `newnote` — только с base64-данными каждого чанка и `size` по декодированным байтам (B3, B4).
- **Атомарность и оптимистичная блокировка** (C1, C2): читать с `_rev` → `PUT` метадокумента с этим `_rev` (сначала новые чанки, потом метадокумент, ничего после); на 409 — понятная ошибка «заметка изменена параллельно, перечитайте».
- **Конфликты**: `GET?conflicts=true`; при непустом `_conflicts` — отказ в записи с явным сообщением (C3).
- **Пакетность и кэш** (C5): `_all_docs` без `include_docs` и с пропуском диапазона `h:`; метаданные пачками `POST _all_docs {keys}`; кэш индекса по `update_seq`; никакого N+1 в vault-wide инструментах.
- Стартовая проверка `GET /{db}` (A6) и версия LiveSync (B14).

### 4.4. `storage_journal.py` — S3 journal-пир

**Локальное состояние** (каталог `S3_STATE_DIR`, по умолчанию `./data`):
- SQLite (WAL): метадокументы (все leaf-rev с `_revisions`-цепочками), winner per doc, чекпойнт: множество обработанных имён journal-файлов, максимальный ключ бакета;
- Чанк-стор: файлы по `h:<id>` на диске, содержимое — как в записи (для `newnote` — base64-текст). Храним чанки, на которые ссылаются текущие winner-ревизии; чанки только старых ревизий не храним (наши записи на них не ссылаются — переиздавать их не понадобится).

**Чтение (replay)**, формат по `journal/journalRecords.ts` и `JournalSyncCore.ts`:
- `ListObjectsV2(StartAfter=<последний обработанный>)`; имена журналов — всё, что не начинается с `_`;
- каждый файл: download → inflate (deflate; если inflate падает — вероятен E2EE или чужой бакет → `UnsupportedVault`) → построчный разбор записей: компактные чанки `~h:<id>\x1f<escaped>\n` (unesc_newline), метаданные — JSON с обязательным `_rev`;
- применение в порядке файла: чанки — upsert по id; метаданные — слияние rev-дерева по правилу CouchDB/PouchDB: leaf-rev добавляется, winner = максимальное поколение, при равенстве — лексикографически больший rev id; сохраняем `_revisions` целиком;
- чекпойнт после каждого файла — прерванный replay продолжается с того же файла.

**Запись (append)**:
- новые чанки: id `h:<sha256hex[:16] контента>` (уникальность и детерминизм; сплиттер upstream — `[DEFER]`); записи чанков — компакт-формат с escape;
- метадокумент: `winner generation + 1` с полной цепочкой `_revisions` от текущего winner; поля по §4.1; soft delete тем же путём;
- имя файла: `max(now_ms, max_existing_key + 1)` с монотонным счётчиком внутри процесса — защита от коллизий имён и от «серверные часы отстают» (иначе `StartAfter` на клиентах пропустит файл);
- упаковка: JSONL → `zlib` deflate level 8 → `PUT` (content-type `application/octet-stream`); контроль чтением-назад: файл, который мы не можем декодировать сами, не выкладываем;
- служебный объект sync-parameters (`_obsidian_livesync_journal_sync_parameters.json`) читаем (протокол/salt), не пишем.

**Совместимость и эпохи (обязательно; воспроизводит поведение upstream):**

- **Milestone-объект** `_00000000-milestone.json` (`LiveSyncJournalReplicator.ts:64`) читаем при старте: `locked: true` → отказ (идёт rebuild); path-identity range с NFC/E2EE/обфускацией → отказ; журналы есть, а milestone без деклараций узлов → отказ («Rebuild from the authoritative Vault»); `node_chunk_info` используется для распознавания версий формата устройств (плагин пользователя — из стора Obsidian, обновляется по релизам; отставание версии обнаруживается по milestone, а не ломается тихо). Сервер — «невидимый писатель»: сам milestone не пишет и узел не регистрирует. Приёмка незарегистрированного писателя живыми клиентами проверяется критерием §8.2(б); если клиент отвергает — добавляется регистрация узла через `uploadIfUnchanged` milestone'а отдельным шагом.
- **Эпоха и очистка бакета**: в чекпойнте храним `journalEpoch = protocolVersion:pbkdf2salt`. При смене эпохи — probe последнего отправленного нами файла по образцу `ensureCheckpointCachesAreFresh` (`JournalSyncCore.ts:343-401`): файл исчез → авто-сброс локального состояния (SQLite + чанк-стор) и полный повторный replay; файл на месте → только обновить epoch. Перед каждым append — контроль, что наш последний отправленный файл всё ещё существует (защита от записи в стёртый мир).

**Модель согласованности**: refresh перед каждой операцией (троттлинг ≤ 1 раз/N сек, N в конфиге) + инструмент `obsidian_refresh`. Параллельная правка с устройства после нашего refresh не отвергается — она образует второй leaf-rev, winner выбирается детерминированно на всех участниках, конфликт показывается штатным UI Obsidian. Это свойство протокола, а не недоработка; задокументировать в README.

## 5. Слой инструментов: фиксы аудита

Слой почти не меняется структурно; обязательные фиксы:

- **D1/D2**: централизованно в `write_note`/`rename_note` (§4.2).
- **D3**: `mode` обязателен; пустой `overwrite` запрещён; `search/replace/heading` при `overwrite` — ошибка.
- **D4**: `obsidian_fetch` возвращает в `content` сырой текст файла целиком (frontmatter внутри); свойства — отдельное поле-представление.
- **D5/D6/D17**: frontmatter через `ruamel.yaml` round-trip; разделители — только отдельные строки; неизменившийся файл не перезаписывать.
- **D7**: prepend — после закрывающего `---`.
- **D8/D9**: общий резолвер ссылок Obsidian (срез `#anchor`/`^block`, `.md`, basename/кратчайший уникальный путь, без учёта регистра; markdown-ссылки и canvas — по возможности).
- **D10/D11**: буквальная подстановка замены в search-replace; `re.error` и подсчёт совпадений через `subn`/`finditer`.
- **D12/D13/D14/D15/D16/D18/D19**: теги к списку строк, regex тегов по правилам Obsidian, заголовки `^#{1,6}\s+`, проверка типов JSON-параметров, рекурсивный `folder`, устойчивый canvas к `{}`/пустым полям, инструменты свойств/тегов только для `.md`, непустые id в canvas.
- **Бинарные файлы** (общая политика): `list/move/duplicate/delete/stats` работают; `fetch` отдаёт метаданные + размер + sha256, текст не пытается; text-edit/properties/tags — отказ с понятным сообщением. **Запись бинарного содержимого (создание/перезапись `.png`, `.pdf` и т.п.) не поддерживается**: `write_note` принимает только текст; бинарные пути в `create/overwrite` → `BinaryNoteError` (решение владельца может расширить; кодек `newnote` нужен для чтения и move/duplicate — переиздания существующих чанков).

Новые инструменты: `obsidian_refresh` (обновить локальное представление; для CouchDB — no-op/кэш), поле `backend` в `vault_stats`.

Помечено P2, не блокирует основную работу;
  - режимы взаимоисключающие (A8 — задокументировать).

## 7. Инварианты безопасности данных (проверяются тестами)

1. Ни одна операция не выполняет `DELETE` чанков; в CouchDB — никогда, в S3 — удаление объектов журнала вообще не выполняется.
2. Единственный способ удаления заметки — soft delete с сохранением `type/path/children`.
3. `write_note` не может затереть существующую цель без явного `overwrite`; same-path rename — no-op/ошибка, не удаление.
4. `size` = длина декодированного тела; `type` соответствует содержимому.
5. Любая запись проходит валидатор пространства имён §4.1.
6. Ответ «успешно» ⇔ изменение фактически зафиксировано (для S3 — после контрольного чтения-назад; для CouchDB — после 201 PUT).

## 8. Критерии готовности (материальные артефакты)

1. **Unit**: кодек journal-записей на векторах из `journalRecords.unit.spec.ts` (upstream); `path2id` на векторах из upstream-тестов пути; rev-дерево/winner на табличных случаях; round-trip frontmatter (`ruamel.yaml`) на примерах порчи из аудита D5; сценарии воспроизведения §5 аудита — все проходятся.
2. **Интеграция S3**: MinIO в docker на машине пользователя; живой клиент — Obsidian пользователя (плагин из стора), отдельный тестовый vault/профайл, подключённый к тестовому бакету; боевой vault не затрагивается. Seed — небольшой тестовый vault (текстовые заметки + пара бинарников), синхронизированный клиентом в тестовый бакет. (а) полный replay сервером → sha256 всех текстовых заметок совпадают с экспортом клиента; (б) сервер пишет правку/создание/soft delete → живой клиент применяет без size-mismatch/warnings (лог LiveSync + скриншот — артефакты); (в) клиент пишет → сервер после refresh видит; (г) прерывание replay на середине → повторный старт сходится. Ручной прогон по чек-листу выполняет пользователь; итог — заполненный чек-лист + артефакты.
3. **Интеграция CouchDB**: CouchDB в docker + живой клиент; те же сценарии плюс регрессии из §5 аудита.
4. Smoke импорта `server.py` на реальном `mcp` 1.x в обоих режимах auth.

Ручная проверка живым клиентом обязательна: у S3-пути нет headless-референса, доверять только юнит-тестам нельзя (анти-фабрикация).

## 9. Отложено (`[DEFER]`, с триггером)

- Порт chunk-сплиттера upstream (дедупликация между файлами/ревизиями). Триггер: заметный рост объёма журнала/базы от серверных записей или запрос дедупликации. Без него корректность не страдает, только эффективность.
- Поддержка E2EE (v1/v2 HKDF из `octagonal-wheels`). Триггер: появление зашифрованного vault в использовании.
- NFC-нормализация и case-sensitive режимы path2id — читать и отказывать; полная поддержка по потребности.
- Hidden File Sync только для чтения — по потребности.

## 10. Решения

- `[DECISION]` Два бэкенда за одним `StorageBackend`, выбор явной переменной, без автодетекта (владелец, 2026-11-17).
- `[DECISION]` CouchDB-слой переписывается с нуля по §4.3, а не патчится (рекомендация аудита §8).
- `[DECISION]` S3-сторона — полный пир с локальным состоянием (SQLite + чанк-стор), не «тонкий читатель»: без локального состояния невозможны ни чтение заметок, ни корректные ревизии для записи.
- `[DECISION]` Конфликт параллельных правок в S3-режиме не предотвращается, а разрешается детерминированным winner'ом поверх rev-дерева — это семантика протокола LiveSync.
- `[GOTCHA]` Имя journal-файла должно сортироваться после всех уже полученных клиентами файлов: при отстающих часах сервера `StartAfter` на клиентах пропустит запись. Защита: `max(now_ms, max_key+1)` + монотонный счётчик.
- `[GOTCHA]` Чанк в journal-записи не несёт `_rev`; приёмная сторона назначает свой. Ревизионная целостность существует только у метадокументов.
- `[REUSE]` Векторы upstream-тестов (`journalRecords`, path, ContentSplitter) — как золотые данные для наших юнит-тестов.

## 11. Что осталось строителю

- Точная схема SQLite (минимум: `docs(rev_tree)`, `chunks_meta`, `checkpoint`) и алгоритм слияния rev-дерева — реализация по правилу §4.4, табличные тесты обязательны.
- Трассировка/логгирование replay (сколько файлов/записей, скорость) — диагностика долгого первого старта.
- Тонкости deflate: upstream использует `wrappedDeflate(level 8)`; проверить совместимость с `zlib` (wbits) на реальных файлах живого клиента до выкатки.
