# Аудит obsidian-livesync-mcp

Дата: 2026-11-10. Объект: `main` @ `c07998f` (последний коммит 2026-06-02, рабочее дерево чистое, других веток нет).

## 1. Итог

**Читать заметки `.md` из незашифрованного vault можно. Писать в боевой vault в текущем виде нельзя.** Сервер воспроизводит формат LiveSync неточно, и запись через него портит базу так, что это не видно ни пользователю, ни модели: инструменты отвечают «успешно».

Главное:

1. **Проект сейчас не ставится по README.** `requirements.txt` разрешает `mcp[cli]>=1.0.0` без верхней границы. Свежий `pip install` берёт `mcp` 2.3.0 (вышел 2026-10-02), а там `mcp.server.fastmcp` при импорте бросает `ModuleNotFoundError`. Вдобавок `python run.py` не читает `.env`.
2. **Модель хранения расходится с upstream LiveSync в четырёх местах, и каждое ведёт к потере или порче данных:**
   - сервер физически удаляет старые чанки, хотя в LiveSync они адресуются по содержимому и общие для разных заметок и ревизий;
   - удаление делается голым HTTP DELETE, и клиенты LiveSync его не применяют;
   - все не-`.md` файлы создаются с бинарным типом `newnote`, но с текстом внутри;
   - E2EE, обфускация путей и Hidden File Sync никак не обрабатываются и не обнаруживаются.
3. **Несколько инструментов теряют данные сами по себе:**
   - перенос заметки на тот же путь или со сменой регистра удаляет её;
   - move и duplicate молча затирают существующую цель;
   - `obsidian_update_note` с аргументами по умолчанию стирает заметку;
   - цикл «fetch → правка → overwrite» теряет frontmatter;
   - перезапись frontmatter портит обычный YAML Obsidian.
4. **Аутентификация в bearer-режиме корректна.** `OAUTH_PASSWORD` же нигде не проверяется: реальная защита OAuth-режима держится только на `OAUTH_CLIENT_SECRET`. Совет из README включить DCR полностью снимает аутентификацию.
5. **Документация** местами описывает не то, что делает код: шаги установки, назначение `OAUTH_PASSWORD`, гарантии из CHANGELOG 1.0.1, состояние тестов в AGENTS.md.

Критических находок (по шкале ниже) нет. Все кандидаты в critical верификаторы понизили до high: файлы на уже синхронизированных устройствах остаются целы, поэтому восстановление обычно возможно. Но восстанавливать придётся вручную, а повреждённая база реплицируется на все устройства.

### Пока проблемы P0 не исправлены

- Подключать сервер только к vault без E2EE и без обфускации путей, с выключенным Hidden File Sync.
- Пользоваться только чтением: `obsidian_fetch`, `obsidian_search`, `obsidian_list_notes`, инструментами ссылок по `.md`.
- Не вызывать `obsidian_move_note`, `obsidian_delete_note`, `obsidian_duplicate_note` и пишущие инструменты на заметках, созданных в Obsidian.
- Ставить зависимости с `mcp[cli]>=1.10.0,<2`.

## 3. Как устроен проект и формат LiveSync

### 3.1. Проект

```
Obsidian (телефон/десктоп) ──LiveSync──> CouchDB <── этот MCP-сервер <── Claude / Codex
```

Сервер ходит в CouchDB напрямую через `httpx` с учётными данными администратора CouchDB.

- **Чтение заметки:** метадокумент `_id = path.lower()` → список `children` → склейка поля `data` из чанков `h:*`.
- **Запись** (`write_note`): весь текст кладётся в один новый чанк, старые чанки удаляются, метадокумент перезаписывается.
- **Аутентификация:** либо статический bearer-токен (`MCP_API_KEY`, имеет приоритет), либо OAuth 2.1 через провайдер в памяти. Без обоих сервер не стартует.

### 3.2. Как на самом деле работает формат LiveSync

Это справка для раздела 4. Все ссылки — на upstream `livesync-commonlib`, если не указано другое.

| Аспект | Upstream | Этот сервер |
|---|---|---|
| Типы заметок | `plain` (текст), `newnote` (бинарь в base64), legacy `notes` (данные внутри документа) | `plain` для `.md`, `newnote` для всего остального, данные всегда сырым текстом |
| ID заметки | `path2id`: lowercase только при `handleFilenameCaseSensitive=false` (по умолчанию для новых vault); ведущий `_` экранируется как `/_`; NFC-нормализация опционально; при обфускации `f:` + keyed hash | всегда `path.lower()` |
| Чанки | Rabin-Karp по содержимому (для текста ~128 Б…~1 КБ, в среднем ~256 Б); `id = "h:" + xxhash64(piece)`, при шифровании `h:+`; **дедупликация между файлами и ревизиями** | один чанк на всю заметку, `id = "h:" + md5(time_ns)[:16]` |
| Обновление | новый метадокумент с новым `children`; **старые чанки не удаляются** | старые чанки удаляются HTTP DELETE |
| Удаление файла | soft delete: та же ревизия с `deleted: true` и новым `mtime`, тело сохраняется (`EntryManagerImpls.ts:731-741`) | голый `DELETE` метадокумента и всех чанков |
| Удаление чанков | только Garbage Collection V3 после анализа достижимости по всем файлам и веткам конфликтов, через `_purge` (`obsidian-livesync docs/specs_garbage_collection.md`) | при каждой записи и удалении |
| Чтение | текст, если `type == "plain"` или путь в `isPlainText` (`.md .txt .svg .html .csv .css .js .xml .canvas`); иначе base64-декодирование каждого чанка | склейка строк без учёта типа |
| Служебные документы | `obsydian_livesync_version`, `syncinfo`, префиксы `i:` (hidden files), `ix:` (customization sync), `ps:` (plugin sync), `f:` (обфускация), `_local/*` | фильтруются только `h:`, `_*` и `obsydian_livesync_version` |
| E2EE | `e_: true`, данные с префиксом `%=` (HKDF) или `%`, id чанков `h:+`; при обфускации `path = "/\\:..."` | не поддерживается и не обнаруживается |
| Применение на клиенте | клиент применяет документ, только если `type` равен `plain` или `newnote` (`isAnyNote`); перед записью сверяет `size` с декодированным размером (`processSizeMismatchedFiles=false` по умолчанию) | тумбстоун без `type`; `size` = длина текста в UTF-8 |

Для сторонних инструментов upstream поставляет `DirectFileManipulatorV2` (`src/API/DirectFileManipulatorV2.ts`). Это лучший образец для исправления слоя хранения.

Совпадает с upstream: набор полей метадокумента (`_id, path, ctime, mtime, size, type, children, eden: {}`), время в миллисекундах, размер в байтах, тип `plain` для `.md`, форма чанка `{_id, data, type: "leaf"}`.

### B. Совместимость с форматом LiveSync

**B1 — high — запись и удаление уничтожают чанки, общие для других заметок и ревизий** · `couchdb.py:169-173` (`write_note`), `couchdb.py:205-208` (`delete_note`), `couchdb.py:226` (`rename_note`)

**Суть.** Upstream адресует чанки по содержимому и дедуплицирует их. По спецификации GC идентификаторы чанков выводятся из содержимого и общие для разных файлов (`docs/specs_garbage_collection.md:40`). Один чанк `h:…` встречается в `children` многих заметок (общий frontmatter, шаблонный абзац, копии) и всех ревизий одной заметки. Сервер при каждой записи, удалении и переносе делает HTTP DELETE на все чанки старой ревизии без проверки ссылок.

**Сценарий** (воспроизведён). `A.md` и `B.md` созданы в Obsidian из одного шаблона и делят чанк `h:shared`. Вызов `obsidian_update_note` на `A.md` удаляет `h:shared`. После этого `read_note_content("b.md")` даёт `Chunk 'h:shared' not found`. Тумбстоун реплицируется на все устройства.

**Последствия:**
- файлы на дисках уже синхронизированных устройств целы;
- `B.md` не собирается из базы на новом устройстве, после rebuild или fetch, в разрешении конфликтов и в истории документа;
- все vault-wide инструменты сервера падают (см. C4);
- «само лечится» только после того, как `B.md` пересохранят в Obsidian уже после прихода тумбстоуна.

Даже без общих чанков удаление ломает Document History и трёхстороннее слияние конфликтов самой `A.md`.

**Исправить:** никогда не удалять чанки и оставить сборку мусора встроенному GC LiveSync. В идеале генерировать чанки так же, как upstream (разбиение по содержимому и xxhash64), чтобы они дедуплицировались с чанками плагина.

**B2 — high — удаление голым `DELETE`: клиенты его не применяют** · `couchdb.py:210`, `couchdb.py:46-51`

**Суть.** Upstream удаляет файл записью новой ревизии с `deleted: true` и новым `mtime`, тело сохраняется. HTTP DELETE создаёт тумбстоун `{_id, _rev, _deleted}` без `type` и `path`. Согласно анализу верификаторов:
- при `readChunksOnline=true` (по умолчанию) устройства тянут изменения с селектором `{type: {$ne: "leaf"}}`, и тумбстоун без поля `type` до них вообще не доходит;
- при `readChunksOnline=false` его отбрасывает проверка `isAnyNote` с записью в лог «Skipped unexpected non-note document» (`ReplicateResultProcessor.ts:504`).

**Сценарий.** `obsidian_delete_note("Inbox/old.md")` убирает документ из CouchDB, но на телефоне и десктопе `Inbox/old.md` остаётся. Следующая правка файла на устройстве возвращает его в базу. `obsidian_move_note("a.md", "b/a.md")` оставляет на устройствах оба файла.

**Исправить:** удалять как upstream — `GET`, затем `deleted = true`, `mtime = now_ms`, сохранить `type`, `path` и `children`, затем `PUT`. Чанки не трогать.

**B3 — high — не-`.md` файлы создаются как бинарные (`newnote`) с текстом внутри** · `couchdb.py:191`

**Суть.** `"newnote" if not doc_id.endswith(".md") else "plain"`. В LiveSync `newnote` означает base64-бинарь. Клиент считает документ текстом, только если `type == "plain"` или расширение входит в `isPlainText`. Поэтому `.canvas`, `.txt`, `.svg`, `.html`, `.csv`, `.css`, `.js`, `.xml` проходят, а `.base`, `.json`, `.yaml` и прочие — нет.

**Сценарий.** `obsidian_create_note("Tasks.base", ...)` (инструмент прямо рекламирует `.base`). Клиент пытается декодировать YAML как base64 и получает пустой буфер. Проверка размера блокирует запись: «seems to be corrupted! Writing prevented». Файл не появляется ни на одном устройстве, а сервер ответил «Created». С `processSizeMismatchedFiles=true` пишется файл нулевой длины.

**Исправить:** любой текст писать с типом `plain`. `newnote` использовать только для base64-данных, кодируя каждый чанк отдельно.

**B4 — high — файлы `newnote`, созданные плагином, читаются как base64 и портятся при записи** · `couchdb.py:105-128`, `couchdb.py:176-182`, `couchdb.py:213-227`, `server.py:347-364`

**Суть.** Для `.base`, `.json`, `.yaml`, синхронизированных из Obsidian, `obsidian_fetch` возвращает base64 вместо содержимого. Пишущие инструменты кладут сырой текст в документ с сохранённым типом `newnote` и записывают в `size` длину текста, а не декодированных байт. Устройства такую правку отвергают проверкой размера, и правка молча не доходит до vault, хотя сервер отвечает «Updated».

К этому пути ведут overwrite, append и prepend, `obsidian_manage_properties` (`set`/`delete`) и `obsidian_manage_tags` (`add`/`remove`). При search-replace текстовый образец почти никогда не совпадает с base64, поэтому записи обычно нет.

**Move и duplicate бинарников** (PDF, картинки) склеивают куски base64, закодированные по отдельности, в одну строку с паддингом в середине и неверным `size`. Новая копия на устройствах не появляется, а старый документ удаляется из базы по механике B1/B2.

**Исправить:**
- для `newnote` декодировать каждый чанк отдельно и склеивать байты;
- текстовые инструменты на бинарных файлах запрещать, либо перекодировать при записи и ставить `size` равным числу декодированных байт;
- move и duplicate делать копированием `children`, не пересобирая содержимое.

**B5 — high (условно) — E2EE: шифротекст читается как текст и записывается обратно открытым текстом** · `couchdb.py:121-127`, `couchdb.py:160-166`

**Условие:** в vault включено сквозное шифрование LiveSync, а обфускация путей выключена (так по умолчанию в схеме настроек; мастер настройки E2EE включает обфускацию сам).

**Суть.** Данные чанков начинаются с `%=` (HKDF) или `%`, у чанков `e_: true`. Сервер проверяет только, что `data` — строка, и выдаёт шифротекст как содержимое заметки. Append, prepend, правки properties и tags, rename, duplicate и canvas записывают шифротекст вместе с правкой новым незашифрованным чанком. Его id без префикса `h:+`, поэтому клиенты не пытаются его расшифровать и принимают.

**Сценарий.** `obsidian_update_note("Daily.md", mode="append", content="- task")` — на всех устройствах `Daily.md` превращается в шифротекст с хвостом `- task`. Любая запись (`create`, `overwrite`) кладёт содержимое на сервер открытым текстом, то есть обходит шифрование, которое настроил пользователь.

**Исправить:** обнаруживать E2EE и отказывать в записи:
- `_local/obsydian_livesync_milestone` → `tweak_values.encrypt` и `usePathObfuscation`;
- на чанке: `e_ === true`, id с `h:+`, данные с `%`;
- на документе: id с `f:`, путь с `/\:`.

Задокументировать, что E2EE не поддерживается, либо реализовать HKDF-шифрование по `src/pouchdb/encryption.ts`.

**B6 — medium — обфускация путей (`f:`): заметки «не найдены», запись создаёт дубль** · `server.py:145-147`, `couchdb.py:156,221`
- При обфускации id заметки равен `f:` + хеш пути. `path.lower()` никогда не совпадает с ним, поэтому чтение, правка, удаление и перенос возвращают «not found».
- `obsidian_create_note` с тем же путём создаёт второй документ с открытым id. Клиент применяет его по `path` и перезаписывает файл, а следующая правка с устройства уходит в `f:`-документ, и копии расходятся.
- При E2EE `list_notes` показывает пути вида `/\:...`.
- **Исправить:** обнаруживать обфускацию и отказывать; при желании реализовать вывод id upstream с паролем пользователя.

**B7 — high (условно) — через Hidden File Sync можно записать плагин в `.obsidian/` на все устройства** · `couchdb.py:156,191`, `server.py:145-147`

**Условие:** у пользователя включён Hidden File Sync (по умолчанию выключен).

**Суть.** Путь от клиента превращается в id без проверки пространства имён. `obsidian_create_note("i:.obsidian/plugins/x/main.js", <код>)` создаёт документ скрытого файла LiveSync. `.js` входит в `isPlainText`, поэтому код записывается как есть. Шаблоны исключения по умолчанию покрывают только `node_modules`, `.git` и `obsidian-livesync`, так что `.obsidian/plugins/*` и `community-plugins.json` применяются на всех устройствах.

`obsidian_update_note(mode="overwrite")` подменяет `main.js` уже установленного и включённого плагина. `obsidian_move_note` и `obsidian_duplicate_note` тоже принимают произвольный `new_path`.

**Риск:** LLM, которую сбил с толку внедрённый промпт (например, из веб-клипа в заметке), может исполнить код с правами Node в десктопном Obsidian на всех устройствах.

**Статус:** путь в коде upstream прочитан (`CmdHiddenFileSync.ts`, `setting.const.defaults.ts:100-103`); сквозной прогон на живом клиенте не делался.

**Исправить:** разрешать только обычные пути внутри vault. Отклонять, без учёта регистра и после срезания ведущего `/`: префиксы `i:`, `ix:`, `ps:`, `h:`, `f:`, `_` и сегменты, начинающиеся с точки (`.obsidian/` и т. п.).

**B8 — medium — `list_notes` показывает служебные документы как заметки** · `couchdb.py:82`
- Фильтр пропускает `syncinfo`, документы `i:`, `ix:`, `ps:`, `f:` и legacy `notes`, и не проверяет `type`. Конфиги Obsidian и плагинов попадают в список, поиск и правки. Документы `ix:` оканчиваются на `.md` и проходят даже фильтр `extension=".md"`.
- У `syncinfo` нет `size`, поэтому `obsidian_vault_stats` падает с `TypeError` (`server.py:743`: `n.get("size", 0)` возвращает `None`, ключ существует).
- **Исправить:** брать документ, только если его `type` равен `plain` или `newnote`, id не начинается со служебного префикса и не равен `syncinfo` или `obsydian_livesync_version`. Одного фильтра по типу мало: документы `i:` тоже `plain`/`newnote`. В `vault_stats` писать `(n.get("size") or 0)`.

**B9 — medium — правила `path → id` не совпадают с upstream** · `server.py:145-147`, `couchdb.py:156,221`
- Upstream хранит пути на `_` под id `/_...`, потому что CouchDB резервирует `_`. Сервер шлёт `_inbox/x.md`, CouchDB отвечает 400, а `list_notes` выдаёт путь, который потом нельзя открыть.

- NFC-нормализация не выполняется.
- `Inbox/x.md`, `/Inbox/x.md`, `./Inbox/x.md` и `Inbox\x.md` дают четыре разных id.
- **Исправить:** одна функция `path2id` по образцу upstream (`src/string_and_binary/path.ts`) с нормализацией ввода, вызываемая и из `server.py`, и из `couchdb.py`.

**B10 — low — служебные пространства имён CouchDB доступны инструментам** · `server.py:145`, `couchdb.py:31-32,156`
- Пути `obsydian_livesync_version`, `_local/*` и `h:<id>` доступны на удаление, а `_design/x` — на запись. Учётные данные администратора CouchDB делают это возможным.
- Запись дизайн-документа выведена из логики разбора пути в CouchDB и не прогонялась на живом сервере.
- Ни один инструмент не раскрывает id чанков, поэтому для удаления чанка id нужно угадать.
- **Исправить:** та же проверка пути, что в B7; ведущий `_` переводить в `/_`, как upstream.

**B11 — low — одна заметка = один чанк; id чанка не по содержимому** · `couchdb.py:146-150,161`
- Нет разбиения и дедупликации. Каждая правка перекачивает заметку целиком, а большая заметка может упереться в `max_document_size` CouchDB (413).
- `md5(time_ns)` не детерминирован; на грубых часах (Windows до Python 3.13) параллельные записи могут получить один id, и вторая запись падает с 409.
- **Исправить:** разбивать текст как upstream (см. B1).

**B12 — low — заметки с soft delete читаются, а правки их воскрешают** · `server.py:177-182`, `couchdb.py:180-181`
- `obsidian_fetch` игнорирует `deleted: true`. `write_note` снимает флаг, поэтому append или правка тегов на заметке, удалённой на телефоне, возвращают её на все устройства.
- **Исправить:** во всех путях чтения считать `deleted: true` отсутствием заметки; воскрешение разрешать только явным `create`.

**B13 — low — legacy-тип `notes` читается пустым** · `couchdb.py:110-112`
- Очень старые vault хранят данные прямо в документе (`type: "notes"` или тип не указан). Сервер возвращает `""`, а его правки клиенты не видят.
- **Исправить:** читать `doc["data"]`; запись запрещать или явно конвертировать в `plain`.

**B14 — info — нет проверки совместимости с vault**
- Upstream-клиенты сверяют `obsydian_livesync_version` и включённые функции. Сервер не проверяет ничего и пишет в vault, формат которого не поддерживает.
- **Исправить:** при старте читать документ версии и milestone, выборочно смотреть несколько документов и отказываться работать при E2EE, обфускации, case-sensitive режиме или NFC.

### C. Надёжность CouchDB-клиента

**C1 — medium — запись и удаление неатомарны: разрушительный шаг идёт до записи метаданных** · `couchdb.py:157-182`, `couchdb.py:204-210`
- Порядок в `write_note`: `GET` метаданных → `PUT` нового чанка → `GET`+`DELETE` каждого старого чанка → `PUT` метаданных с исходным `_rev`.
- Таймаут, сетевая ошибка или 5xx на последнем шаге оставляют метаданные со ссылками на удалённые чанки: заметка не читается, новый чанк осиротел.
- При 409 от параллельной записи LiveSync заметка ломается, если новая ревизия ещё ссылается на удалённые чанки, а при дедупликации upstream это вероятно.
- В `delete_note` то же самое: сначала удаляются чанки, потом метаданные с `_rev`, полученным заранее.
- CHANGELOG 1.0.1 обещает, что «сбой посреди записи не может безвозвратно повредить документ». Окно сбоя сдвинуто, но не закрыто (см. F2).
- **Исправить:** новый чанк → `PUT` метаданных → всё, чанки не удалять. На 409 перечитать документ и вернуть понятную ошибку «note changed concurrently».

**C2 — medium — нет оптимистичной блокировки: потерянные обновления** · `couchdb.py:157`, все read-modify-write инструменты
- Инструмент читает содержимое и выбрасывает `_rev`; `write_note` берёт свежий `_rev` и записывает. Правка с телефона, пришедшая между чтением и записью, затирается без 409, и её чанки удаляются.
- Два параллельных вызова на одну заметку (например, `obsidian_manage_tags` и `obsidian_manage_properties`) теряют одно из обновлений.
- **Исправить:** возвращать `_rev` из чтения, передавать в запись и отказывать при несовпадении.

**C3 — medium — `_conflicts` игнорируются** · `couchdb.py:34-39,210`
- Инструменты работают с победившей ревизией и не знают о конфликтах.
- `delete_note` удаляет только победителя, и CouchDB поднимает проигравшую ветку: «удалённая» заметка возвращается со старым содержимым, часто уже без чанков (B1).
- **Исправить:** читать с `conflicts=true`; при непустом `_conflicts` отказывать в записи или явно разрешать все листья.

**C4 — medium — один битый чанк ломает все vault-wide инструменты** · `couchdb.py:116-127`
- `read_note_content` на отсутствующем чанке бросает `ValueError`; так и задумано в 1.0.1.
- `search_content`, `get_all_tags`, `get_backlinks` и `get_link_graph` вызывают его в цикле без обработки ошибок. Одна повреждённая заметка (в том числе из-за B1) роняет поиск, теги, граф ссылок, поиск сирот и хабов, а также `vault_stats`.
- **Исправить:** ловить ошибку для каждой заметки отдельно, пропускать её и перечислять пропущенные пути в ответе.

**C5 — medium — каждый вызов скачивает всю базу, а затем ещё N+1 запросов** · `couchdb.py:53-62,76`, `couchdb.py:105-128`
- `list_notes` вызывает `_all_docs?include_docs=true` без диапазона ключей и получает все чанки с данными, то есть весь контент vault со всей неубранной историей. Потом чанки отбрасываются в Python, а `resp.json()` держит всё в памяти.
- Vault-wide инструменты затем ещё раз последовательно делают `GET` каждой заметки и каждого чанка: без `asyncio.gather`, `_bulk_get` и кэша. `vault_stats` делает полный проход дважды.
- **Исправить:** список id получать без `include_docs`, пропуская диапазон `h:`; метаданные брать пачками через `POST _all_docs {keys}` или `_find` по `type`; чанки — пачками. Кэшировать индекс по `update_seq` или через `_changes`.

**C6 — low — таймауты: 30 с на фазу, без общего дедлайна** · `couchdb.py:21`
- `httpx` применяет 30 с к connect, read, write и pool по отдельности, поэтому большой `_all_docs` таймаутом не оборвётся.
- Реальные проблемы: память (C5), нет общего дедлайна на вызов инструмента и неясный итог записи после таймаута.
- **Исправить:** явный `httpx.Timeout(connect=5, read=30, write=30, pool=5)` и `anyio.fail_after` на vault-wide инструменты.

**C7 — low — ошибки `httpx` отдаются клиенту как есть** · `couchdb.py:38,43,50,60,69`
- Обрабатывается только 404. На 401, 403, 409, 413 и 5xx модель получает текст вида `Client error '409 Conflict' for url 'http://localhost:5443/obsidian/...'`: внутренний адрес, порт, имя базы и id документа. Пароли не утекают, если они не вписаны в `COUCHDB_URL`.
- **Исправить:** сопоставить ошибки с понятными сообщениями (401/403 → «ошибка авторизации CouchDB», 409 → «заметка изменена параллельно, перечитайте», 5xx → «CouchDB недоступна»), а подробности писать только в лог сервера.

**C8 — info — мёртвый код**
- `CouchDBClient.find()` не вызывается; не используются импорты `base64` (`couchdb.py:3`), `time` и `copy` (`server.py:7-8`).
- HTTP-клиент создаётся при импорте и никогда не закрывается; для одного долгоживущего процесса это безвредно.
- **Исправить:** удалить; при желании создавать клиент в lifespan FastMCP.

### D. Корректность инструментов

Все пишущие инструменты идут через `write_note`, поэтому на любой заметке, созданной в Obsidian, к ним дополнительно применяются B1, C1 и C2.

**D1 — high — перенос на тот же путь или со сменой регистра удаляет заметку** · `couchdb.py:213-227`, `server.py:332-344`
- Если `new_path.lower() == old_id`, `write_note` переписывает тот же документ, а потом `delete_note(old_id)` удаляет и его, и свежий чанк.
- **Воспроизведено:** `obsidian_move_note("A.md", "A.md")` → «Moved», потом `obsidian_fetch("A.md")` → «not found». То же для `"B.md" → "b.md"`. Удаление при этом реплицируется на устройства.
- **Исправить:** проверять это в `rename_note`. При смене только регистра обновлять поле `path`; при одинаковом пути ничего не делать.

**D2 — high — move и duplicate молча затирают существующую цель** · `couchdb.py:176-182,219`, `server.py:363`
- `write_note(create=True)` на деле означает «создать или перезаписать».
- **Воспроизведено:** `obsidian_move_note("C.md", "D.md")` → `D.md` теперь содержит текст `C.md`; `obsidian_duplicate_note("E.md", "F.md")` → `F.md` затёрт.
- Повторный `duplicate` без `new_path` затирает уже отредактированную `X copy.md`.
- `obsidian_create_note` и `obsidian_create_from_template` цель проверяют, эти два инструмента — нет.
- **Исправить:** централизованно в `write_note` — при `create=True` и существующем неудалённом документе бросать ошибку или требовать явный флаг `overwrite`.

**D3 — high — `obsidian_update_note` с аргументами по умолчанию стирает заметку** · `server.py:250-251,276-277`
- `mode="overwrite"` и `content=""` по умолчанию.
- **Воспроизведено:** вызов только с `path` даёт «Updated (overwrite)» и пустую заметку.
- Чаще это случается, когда модель передаёт `search` и `replace`, но забывает `mode`: заметка стирается вместо замены.
- **Исправить:** сделать `mode` обязательным; запрещать overwrite с пустым `content` без явного флага; отклонять `search`, `replace` и `heading` в режиме overwrite.

**D4 — high — цикл «fetch → правка → overwrite» теряет frontmatter** · `server.py:185-189,276-277`
- Для `.md` `obsidian_fetch` по умолчанию (`include_properties=True`) возвращает в `content` тело без YAML-блока, а свойства — отдельным словарём или вообще без них, если разбор дал `{}`.
- Обычный цикл LLM: прочитать, поправить, записать `content` обратно через overwrite. После него все свойства и теги исчезают. Ни одна docstring об этом не предупреждает.
- **Исправить:** возвращать в `content` сырой текст файла, а свойства — как дополнительное представление только для чтения. Либо сохранять существующий frontmatter при overwrite, если вызывающий не передал свой.

**D5 — high — перезапись frontmatter портит обычный YAML Obsidian** · `server.py:82-124` (разбор), `server.py:127-142` (сериализация), вызовы в `server.py:422-445,490-508`

**Суть.** `obsidian_manage_properties` (`set`/`delete`) и `obsidian_manage_tags` (`add`/`remove`) пропускают весь frontmatter через самописные разборщик и сериализатор. Это происходит даже когда ничего не меняется: удаление отсутствующего ключа всё равно переписывает заметку.

**Воспроизведено на примерах:**
- `related: "[[Other]]"` → `related: [[Other]]`, что YAML читает как вложенный список;
- `title: 'Re: meeting'` → `title: Re: meeting`, невалидный YAML, и Obsidian отвергает весь блок;
- список без отступа (`tags:\n- a`) разбирается в `{}`: при записи весь frontmatter пропадает, а `manage_tags add` заменяет существующие теги одним новым;
- вложенные словари уплощаются (`author.name` → `name`);
- блочные скаляры `|` обрезаются;
- строки комментариев теряются;
- типы дрейфуют (`01234` → `1234`, `1.10` → `1.1`, строковые `'42'` и `'true'` становятся числом и bool);
- пустые ключи (`aliases:`) теряются;
- `None` записывается строкой `None`.

**Исправить:** `ruamel.yaml` в round-trip режиме; ещё лучше — править только строки нужного ключа и оставлять остальное байт в байт. Не переписывать файл, если ничего не изменилось.

**D6 — medium — закрывающий `---` ищется где угодно** · `server.py:84-86`

### E. Аутентификация и безопасность

**E1 — medium — `OAUTH_PASSWORD` нигде не проверяется** · `oauth_provider.py:59,84-102`, `server.py:55`
- Пароль сохраняется в `self.access_password` и больше не читается. Страницы согласия или ввода пароля нет. `authorize()` сразу выдаёт код, а комментарий на `oauth_provider.py:87-88` («проверка пароля на уровне страницы /authorize») ложен.
- `OAUTH_PASSWORD` работает только как переключатель режима (`auth_config.py:12`).
- **Что защищает на самом деле.** SDK проверяет `client_id`, точное совпадение `redirect_uri` и PKCE S256. Без `OAUTH_CLIENT_ID` атакующий не получит код. С известным `client_id` (по дизайну OAuth это не секрет) он получает код прямо из `Location` ответа `/authorize`, но без `OAUTH_CLIENT_SECRET` не обменяет его на токен. Итого единственный реальный секрет — `OAUTH_CLIENT_SECRET`, и он должен быть с высокой энтропией.
- **Исправить:** настоящая страница входа (`@mcp.custom_route`, POST-форма, `hmac.compare_digest` на байтах, ограничение частоты попыток, код выдаётся только после неё). Либо убрать `OAUTH_PASSWORD` и честно задокументировать, что защита держится на секрете клиента.

**E2 — high (условно) — совет README включить DCR снимает аутентификацию** · `README.md:148`, `oauth_provider.py:81-82`
- **Условие:** оператор последует совету README и поставит `ClientRegistrationOptions(enabled=True)`.
- Тогда кто угодно, зная только URL, регистрирует клиента через `POST /register` (SDK сам вернёт ему `client_secret`), получает код от автоодобряющего `/authorize` и обменивает его со своим PKCE. В итоге у него токен с полным чтением, записью и удалением vault. Каждая регистрация растит словари в памяти без ограничения.
- README называет это «кто угодно сможет зарегистрировать клиента», что звучит как неудобство, а на деле это отсутствие аутентификации.
- **Исправить:** убрать совет или прямо написать, что без E1 он даёт полный доступ; не стартовать с включённым DCR, пока `authorize()` одобряет всё подряд.

**E3 — low — `0.0.0.0` и обычный HTTP; TLS-прокси подразумевается, но не описан** · `server.py:31,40-42`, `README.md:81-82`
- Uvicorn отдаёт обычный HTTP на `:8484` всем интерфейсам. Если порт не закрыт файрволом, bearer-токен, `client_secret`, коды авторизации и содержимое vault ходят открытым текстом.
- Жёстко прописанное `enable_dns_rebinding_protection=False` влияет только при loopback-хосте: для `0.0.0.0` SDK и так выключает защиту. На loopback это, вероятно, сделано намеренно: прокси передаёт публичный `Host`, и иначе каждый запрос получал бы 421.
- **Исправить:** по умолчанию `MCP_HOST=127.0.0.1`; при необходимости явные `allowed_hosts` и `allowed_origins` (покрывают только `/mcp`); описать в README обратный прокси (TLS, проброс `Authorization`).

**E4 — low — используются учётные данные администратора CouchDB** · `README.md:74-75`, `.env.example:2`
- Серверу нужны только права участника одной базы, а он получает права создавать и удалять базы, править `_users` и `_config`. Вместе с B10 украденный токен MCP даёт запись дизайн-документов.
- **Исправить:** описать отдельного пользователя в `_security.members.names` нужной базы.

**E5 — low — ReDoS блокирует весь сервер** · `couchdb.py:234-240`, `server.py:303`
- Пользовательский regex выполняется синхронно в event loop по каждой заметке. Шаблоны вроде `(\w+\s?)+X` на обычном тексте работают экспоненциально долго: 2,14 с на 30 символах, замерено. Пока шаблон считается, все MCP-сессии и OAuth-эндпоинты висят.
- **Исправить:** модуль `regex` с `timeout=` или выполнение в отдельном убиваемом процессе; ограничение длины шаблона.

**E6 — low — не-ASCII символы в `Authorization` дают 500** · `auth_config.py:29`
- `hmac.compare_digest` на `str` с не-ASCII символами бросает `TypeError`, и SDK его не ловит. Обхода нет, но вместо 401 возвращается 500 с трассой в логе.
- **Исправить:** сравнивать `token.encode()` с `expected.encode()`; не стартовать с коротким `MCP_API_KEY` или `OAUTH_CLIENT_SECRET`.

**E7 — low — OAuth-хранилища в памяти: растут без ограничения и теряются при рестарте** · `oauth_provider.py:60-63,91,109-111`
- Каждый `/authorize` с известным `client_id` добавляет код. Просроченные записи удаляются, только если к ним снова обратились, поэтому брошенные коды и неиспользованные токены живут вечно.
- Старый access-токен остаётся валидным до 24 часов после refresh.
- Любой рестарт, в том числе `Restart=always` systemd, сбрасывает все токены, включая 30-дневные refresh, и коннекторы приходится переподключать.
- **Исправить:** чистить просроченное при каждой операции; ограничить число кодов; хранить хеши токенов в файле или SQLite.

**E8 — low — systemd-юнит без изоляции; права на `.env` не описаны** · `obsidian-mcp.service`
- Нет `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `RestrictAddressFamilies`, `MemoryMax`, `StartLimitIntervalSec`.
- `.env` лежит в каталоге, куда может писать сам сервис; про `chmod 600` ничего не сказано.
- **Исправить:** добавить стандартные директивы изоляции; `.env` должен принадлежать root с правами `0600`.

**E9 — info — OAuth-режим не проверяет scopes** · `server.py:60-68`
- В `AuthSettings` нет `required_scopes`, поэтому токен с `scopes=[]` принимается. Пока клиент и scope одни, на практике ни на что не влияет.

## 8. План исправлений

Главный источник проблем — слой хранения в `couchdb.py`, написанный по собственной модели вместо модели LiveSync. Его разумнее переписать по образцу upstream (`EntryManager`, `DirectFileManipulatorV2`): разбиение по содержимому и xxhash64, soft delete, тип по содержимому, декодирование `newnote`, никаких удалений чанков, запись с проверкой `_rev`. Это одно цельное изменение, а не серия заплаток поверх B1–B4 и C1–C3. Это рекомендация; решение за владельцем.

**P0 — до любой записи в боевой vault**
1. A1: `mcp[cli]>=1.10.0,<2` или точный пин, lock-файл, объявить `pydantic` и `python-dotenv`; A2: загрузка `.env`.
2. B1: не удалять чанки нигде.
3. B2: soft delete как в upstream.
4. B3 и B4: тип `plain` для текста; декодирование `newnote` при чтении; запрет текстовых правок бинарных файлов или корректное кодирование с правильным `size`.
5. B5, B6, B14: при старте обнаруживать E2EE и обфускацию и отказывать в записи.
6. B7, B9, B10, D18: одна функция `path2id` с проверкой пространства имён и нормализацией.
7. D1 и D2: в `write_note(create=True)` и `rename_note` запрет затирания и обработка смены регистра; D3: обязательный `mode`, запрет пустого overwrite.

**P1 — корректность и надёжность**
1. D4–D7, D17: frontmatter через точечную правку или `ruamel.yaml`; `obsidian_fetch` возвращает сырой текст; prepend после frontmatter.
2. C1–C3: запись с проверкой `_rev`, сначала метаданные, обработка 409 и `_conflicts`.
3. C4, C7: устойчивость vault-wide инструментов и понятные сообщения об ошибках.
4. C5: убрать скачивание всей базы и N+1, кэш индекса по `update_seq`.
5. D8–D11: резолвер ссылок, буквальная подстановка замены, обработка ошибок regex.
6. G1: тесты `couchdb.py` и инструментов на сценариях из раздела 5, изоляция стабов, HTTP-тесты аутентификации.

**P2 — безопасность развёртывания и документация**
1. E1 и E2: страница входа для OAuth или честная документация; убрать совет про DCR.
2. E3, E4, E8: `127.0.0.1` по умолчанию, описание прокси, отдельный пользователь CouchDB, изоляция в systemd, права на `.env`.

5. F1–F10: README, AGENTS.md, CHANGELOG, docstrings.
6. Оставшиеся low-пункты D12–D16, B11–B13.
